# Именование файлов и секций

Правила действуют для локальной копии и репозитория GitHub: Git хранит те же относительные пути, что находятся в рабочей папке. Новые имена должны совпадать по регистру во всех ссылках, чтобы сборка работала и на Linux.

| Что именуем | Правило | Пример |
| --- | --- | --- |
| Каталоги, маршруты, файлы спецификаций и данных | Строчные латинские буквы, цифры и дефисы (`kebab-case`) | `geoflow-holiday`, `technical-demonstration-spec.md` |
| Изображения, иконки и другие собственные ресурсы | `kebab-case` без пробелов и кириллицы; роль и устройство в конце | `map-desktop.png`, `api-key-mobile.png`, `constructor-desktop-1.png` |
| React-компоненты и одноимённые стили | `PascalCase.tsx` и `PascalCase.module.css`; имя соответствует экспортируемому компоненту | `TechnicalDemonstration.tsx` и `TechnicalDemonstration.module.css` |
| Файлы, имя которых задаёт Next.js | Сохраняем зарезервированное имя | `app/page.tsx`, `app/layout.tsx`, `app/page.module.css` |
| Локальные шрифты | Каталог `app/fonts/`; оригинальные имена поставщика сохраняем | `SuisseIntl-Regular.otf` |

Для нового лендинга используем один читаемый slug в `app/<slug>/page.tsx`, `content/<slug>.ts` и `public/images/<slug>/`. Для карточек с несколькими изображениями добавляем порядковый номер с 1. Имена ресурсов в коде и документации записываем точно как на диске, без URL-кодирования пробелов.

**S01–S10 — постоянные ID типов секций**, а не номера шагов лендинга. Их русские названия и соответствие компонентам находятся в [каталоге](landing-blocks-spec.md). Видимые заголовки секций задаются контентом страницы. Технические имена компонентов и файлов не переименовываются при изменении маркетингового заголовка; это сохраняет стабильные импорты и паспорта. Порядок компонентов в `app/<slug>/page.tsx` соответствует ТЗ конкретного лендинга.

Заголовок H1 каждого паспорта секции начинается с того же ID и названия, что указаны в каталоге и в [индексе паспортов](README.md). При изменении канонического названия обновляем эти три места и корневой README одновременно; имя файла или компонента меняем только при изменении его технической роли.

При добавлении или переименовании ресурса одновременно обновляем все пути в `content/`, компонентах, предпросмотрах, проверочных скриптах и спецификациях. После этого проверяем существование путей и выполняем production-сборку.
