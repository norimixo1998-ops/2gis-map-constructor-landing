# Как дать команде пользоваться библиотекой лендингов

## Решение для инструкции

Между готовым текстом (шаг 2.2) и генерацией страницы (шаг 3) добавить шаг **«Получить версию библиотеки и составить карту блоков»**. В инструкции указывать один адрес библиотеки и конкретную версию (тег или номер релиза). Человек открывает каталог блоков, выбирает блоки по смыслу текста, заполняет карту соответствия, затем передаёт сборщику **эту версию** спецификаций, компонентов и визуалов. Общий style prompt остаётся дополнением о тоне и бренде, а не источником сетки и поведения секций.

## Где хранить

**Предпочтительно:** репозиторий организации в GitHub/GitLab с доступом для маркетинга, дизайна и разработки. Текущий `origin` указывает на личный `norimixo1998-ops/2gis-map-constructor-landing`; его можно использовать для разработки, но корпоративная инструкция не должна зависеть от личного аккаунта. Перенос или зеркалирование в пространство команды требует решения владельца репозитория и администраторов организации. До этого можно выдавать архив фиксированной версии из текущего проекта, явно указывая дату и номер сборки.

**Если человек работает без Git:** в инструкции дать ссылку «Скачать библиотеку ZIP, версия X» из релиза того же репозитория. Архив и репозиторий должны собираться из одного коммита, чтобы паспорта и компоненты не расходились. Пересылка отдельных файлов в чат плохо сохраняет связи между ними.

**Если генератор не может открыть репозиторий:** приложить архив релиза к задаче. Если может — указать URL репозитория и тег версии. Ссылка на произвольную ветку `main` менее воспроизводима: завтра содержимое изменится.

## Что должно быть в версии библиотеки

| Часть | Зачем нужна | Есть сейчас |
| --- | --- | --- |
| `specs/landing-blocks-spec.md` | Каталог B01–B07: назначение, поля, варианты и ограничения | Да |
| `specs/*-spec.md` | Паспорта выбранных блоков, включая адаптив и состояния | Необязательный B03 по Figma добавлен; визуал и мобильную композицию требуется согласовать |
| `landing-prototype/components/` | Реальные компоненты и стили | Да, но не все варианты выделены как самостоятельные компоненты |
| `landing-prototype/app/globals.css`, шрифты, общая оболочка | Визуальные токены и базовая рамка страницы | Да, пока привязаны к прототипу |
| `landing-prototype/public/` | Утверждённые общие визуалы | Частично; изображения другого продукта нельзя автоматически переносить на новую страницу |
| `landing-prototype/content/` и пример маршрута | Показывают отделение текста от компонента | Да |
| `README` для потребителя | Куда поместить текст, как выбрать блоки и запустить проверку | Нужно оформить перед выдачей команде |
| Версия и перечень совместимых блоков | Фиксируют, какой набор получил сборщик | Нужно добавить при первом релизе |

Текущая папка — **прототип библиотеки**, а не полностью упакованный продукт для всей команды. Необязательный B03 «Для кого» по Figma с шестью названиями сфер добавлен для акции; до включения в общий релиз нужны согласованный визуал и проверка адаптива. Существующий `SolvedTasks` с обязательным слотом изображения остаётся отдельной композицией.

## Как это выглядит для человека, который следует инструкции

1. Получить финальный маркетинговый текст и открыть ссылку на библиотеку версии X.
2. Открыть каталог, сопоставить каждый смысловой фрагмент с ID блока и вариантом. Для акции: `B01 → условия акции → B02 → B03 → B05 → B06 → B07`.
3. В таблице отметить для каждого блока текст, источник, статус согласования, визуал и основной CTA. Если варианта нет, оформить локальный паспорт и передать его на дизайн-ревью.
4. Дать генератору доступ к репозиторию на теге X или приложить ZIP того же релиза; приложить финальный текст и таблицу. Попросить использовать компоненты, а не рисовать их по памяти.
5. Проверить предпросмотр на 375, 768, 1024 и 1440 px, переносы, визуалы, действия кнопок и соответствие тексту.

## Что нужно сделать перед включением ссылки в общую инструкцию

1. Выбрать корпоративное место хранения и ответственного за библиотеку.
2. Оформить первый релиз с каталогом, паспортами, компонентами, шрифтами/правами на их использование, общими визуалами и коротким README.
3. Провести дизайн-ревью мобильной композиции B03, выбрать изображение и проверить локальные акционные варианты.
4. Проверить путь пользователя на чистом скачивании/клоне: найти блок, заполнить контент, собрать страницу, увидеть результат.
5. В Confluence закрепить ссылку на релиз и короткую инструкцию из пяти пунктов выше.

Хранить можно и в другом корпоративном хранилище, если оно даёт те же свойства: стабильный адрес, версии, доступ команде, единый пакет спецификаций и компонентов. Для кода Git-репозиторий обычно проще, поскольку страница собирается из этих компонентов.
